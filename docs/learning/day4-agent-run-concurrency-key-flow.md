# Day4 重点：Agent Run 的并发分层流程

> 状态：重点复习锚点。后续学习 MySQL 行锁与事务隔离、分布式幂等、线程池/虚拟线程、Spring AI 模型限流、可观测性与故障排查时，必须回到本例重新对照。

## 真实场景

同一时刻到达四个请求：

| 请求 | 用户 | 幂等键 | 会话 | 含义 |
|---|---|---|---|---|
| A | `user1` | `K100` | `c1` | 首次创建 AI Run |
| B | `user1` | `K100` | `c1` | A 的网络重试 |
| C | `user1` | `K200` | `c2` | user1 的另一项新请求 |
| D | `user2` | `K300` | `c9` | user2 的独立请求 |

## 分层与边界

```text
HTTP 工作线程接收请求
    ↓
同一 userId 的 Database Gate 串行准入判断
    ↓
幂等键：相同请求复用旧 Run，不重复创建
    ↓
活动 Run 规则：同会话最多 1 个、同用户最多配置数量
    ↓
事务提交后释放 Gate
    ↓
Executor 在后台处理新建 Run（重放 Run 不重复启动）
    ↓
Semaphore 限制同一 Agent 实例同时调用模型的数量
```

## Gate、幂等与 Semaphore 不做同一件事

| 机制 | 它问的问题 | 作用范围 | 本例结果 |
|---|---|---|---|
| Database Gate | 同一用户的准入判断能否同时执行？ | Agent 数据库中同一 `userId` 的 Gate 行；可跨 Agent 实例 | A、B、C 按顺序判断；D 可并行 |
| 幂等键 | 这是不是同一件已经提交过的请求？ | 持久化请求标识 | B 找到 A 的 `Run-001`，返回重放结果 |
| Run 准入规则 | 这是新请求时，是否还有会话/用户活动 Run 名额？ | Agent 业务状态 | C 只有在会话和用户均未超限时才能创建新 Run |
| Executor | 新建 Run 由谁在后台执行？ | 当前 Agent 服务进程 | 新建 Run 不长期占 HTTP 工作线程 |
| Semaphore | 当前能否再占用一次模型调用资源？ | 当前 Agent 实例的模型调用资源 | 已运行 Run 在调模型时受限，不决定能否创建 Run |

## 关键顺序

1. A 先取得 `user1` Gate，在事务内查 `K100`、查活动 Run、创建 `Run-001`，提交后释放 Gate。
2. B 后取得 `user1` Gate，发现 `K100` 已对应 `Run-001`，直接返回该 Run，标记为重放；不新建 Run，也不重复启动后台处理。
3. C 后取得 `user1` Gate，`K200` 不存在，因此它是新请求；它必须按最新状态检查同会话和同用户的活动 Run 上限。
4. D 使用 `user2` 的另一条 Gate，不等待 A/B/C；它可并行做自己的判断。
5. 所有新建 Run 提交后才进入后台执行。模型并发满时，Semaphore 的 `tryAcquire()` 会让当前模型调用安全失败或降级；它不会撤销已经创建的 Run，也不替代 Gate/幂等。

## 必须纠正的理解

- Gate 不是每张表的标配，也不是跨服务数据库锁。
- Gate 不是保证一个用户永远只有一个 Run，而是让同一用户的"创建 Run 准入判断"串行。
- `agent_run` 的每一行代表一次具体 Run；它不是始终存在、专门代表用户级准入的固定行。Gate 行正是为这个稳定锁定目标而准备。
- 只有准备创建新 Run 时才检查上限；相同幂等键的重试先复用旧 Run，不能被错误判为超限。
